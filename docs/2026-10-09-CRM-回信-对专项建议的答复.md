### 2.2 同意但需增强后方可实施（两处）

**① A2 缺一个前置：结构化错误码（否则"按 reason 分级"不可实施）**

贵方要求 catch 按 reason 分级。但实测 CRM 侧抛的是**泛型 Error**：

```js
// src/decision/autonomyEngine.js:161
if (!scenario.rows[0]) throw new Error(`未知决策场景: ${scenario_id}`);
```

无 `code`、中文消息 ⇒ catch 侧**无法机器判别**"未知场景 / 维度不合 / 内核异常"，只能字符串匹配（脆弱）。
⇒ 我方增设 **T0：结构化错误码**（`UNKNOWN_SCENARIO` / `DIM_MISMATCH` / `ENGINE_FAULT`），保留 `message` 供人读，作为 A2 的硬前置。

**同时需澄清一处**：`autonomyEngine.js:167` 明载策略版本解析是**故意 fail-open（I1）**，以 `emit('trace') + recordFailure` 补偿（"不留假绿"）。故 A2 **不是把 catch 一律改 fail-closed**，而是按 `code` 分级：`UNKNOWN_SCENARIO` 必须 `ok:false`；`ENGINE_FAULT`/自治度不足允许降级但须带 `degraded:true`。

**② A1 注册表范围远大于两个键：须覆盖 27 键 / 三套命名族**

贵方点名了 `config_change` 与 `config-change`。但 CRM 实际有三套命名族：

| 命名族 | 形态 | 语义 | 数量 |
|---|---|---|---|
| 销售域 | `LEAD_FIT` / `OPP_QUALIFY` / `QUOTE_PRICING` / `REVIEW_GATE` / `SIGN_RISK` … | 销售方法论决策 | 22（已播种） |
| 治理留痕 | `config_change`（下划线） | 平台治理第 0 闸 | 1（已播种） |
| 配置中心键写入 | `config-change` / `llm-config-change`（连字符） | 配置写铸决策 | 2（**未播种**） |
| 待确权 | `CONFIG_WRITE` | 调用 1 处，**未播种** | 1 |

⇒ 注册表初始 = **24 已播种 + 3 未播种调用键 = 27 键**。
**守卫①必须在 27 键全部登记后才通电**——否则对 22 个销售域键产生 22 条假红，与真失败混淆。

**③ A3 建议扩面**：维度散写只是表象，`src/llm/embeddingClient.js:18-26` 还复用 chat 的 `llm_config` 且要求 `apiKey` 非空 ⇒ **免密本地端点被静默降级**。我方把 embedding 配置耦合一并纳入收敛。

### 2.3 不采纳（一条，属我方红线）

**🔴 A1 守卫②"本地 vs 生产库对拍"不采纳。**

CRM 仓的既有红线是：**开发 / 测试 / 探针 / 自动化脚本绝禁指向 `81.70.184.198:5432`**（该红线本身源于多次事故）。把生产库接入**日常门禁**，等于以"护栏"名义重新打开那道事故口。

**我方替代方案**：
- 由注册表单向**生成**种子 SQL（消除手工副本漂移）；
- 门禁**只对本地库**对拍（注册表 ⇄ 本地库一致性）；
- 生产漂移检测走**一次性、HITL 审批**的只读探针，不进日常门禁。

### 2.4 附条件采纳（一条）

**A5（授权同源）**：同意方向，但贵方要求"放行集**相等**而非子集"——若现状存在既定差异，直接判等会红一片。我方处置：**先做 parity 测量**量化 delta，再定收紧节奏；本轮不施工，列入下一轮。

**D3（删除重复播种副本）**：同意收敛方向，但 CRM 禁 DELETE 红线 ⇒ 改为"**单一源 + 另一处改指针注释**"，不做物理删除；且改种子 SQL 属破坏性操作，须先 No-op 迁移验证 + HITL。

## 3. 我方补充的一条施工顺序铁律（贵方排序虽对，但未点破因果）

**`登记+补播种` 必须严格早于 `通电`。**

`config-change`（produce 7 + require 5）、`llm-config-change`（4）、`CONFIG_WRITE`（1）**均未在播种 SQL 中**，当前靠 `configDecision.js` 的 catch 静默放行才没炸。一旦按 A2 改 fail-closed 而键仍缺失，**配置写会从"静默放行"直接变成"硬中断"**——把假阴性修成真事故。
`db/seed.sql:367-369` 早已预警该回归路径（"缺行 → throw 未知决策场景 → 降级 decisionId=null → 调用方 fail-closed → 功能回归"）。

⇒ 我方把它显性化为**门禁前置条件**，而非建议性排序。

## 4. 新增底座要求（R1–R8）

> 背景：贵方多项能力已交付，但**交付形态是 Python 代码**；CRM 是 Node 生产系统，**无法 import**。因此我方诉求从"请给我能力"转为"请给我**可跨语言复现的判据与稳定的引用标识**"。

### R1【最高优先】发布机器可读的"能力清单"，用**稳定能力 ID** 取代 `file:line` 锚点

- **根因**：本轮**双方都因锚点漂移误判**——我引用 `MEMORY_EXPERIMENTAL` `:304` 已漂到 `:419`；我判 F-02 缺失，其实早已 Ship。跨仓用 `file:line` 互引，本质是不可靠的耦合。
- **现状**：贵方已有 `packages/chiyu-kernel/src/chiyu_kernel/contract/manifest.json`，但内容是 **7 个文件的 sha256 哈希**，是**完整性清单**，不承载能力状态，无法用于跨仓引用。
- **要求**：新增/扩展一份 **capability manifest**，字段至少含：`capability_id`（稳定、不随重构变）、`package`、`status`（`shipped` / `experimental` / `planned`）、`semantics`（语义摘要）、`verify_entry`（验证入口命令）、`since_version`。跨仓引用一律用 `capability_id`，并在 CI 中校验引用有效。
- **价值**：一次投入，永久消除跨仓锚点漂移这一类误判。

### R2 判据请提供**语言无关规格**，而非仅 Python 实现

- 贵方 F-05（`register_scenario` 重复登记即抛）、F-06（门面覆盖 + 变异工具）、F-08（零残留 lint）都是**判据**而非仅是代码。
- **要求**：为每条判据补一份语言无关规格：`前置条件 / 触发输入 / 失败语义 / 变异自证方法 / 验收判据式`。
- **价值**：CRM 可照此写 Node 等价件，并**被验证同强度**——这是"判据移植"路线能否成立的前提。

### R3 场景注册表请明确支持"命名族共存"并提供键规范化 lint

- CRM 存在三套命名族（大写下划线 / 小写下划线 / 小写连字符），且 `config_change` 与 `config-change` **语义不同必须共存**。
- **要求**：明确"语义不同即不同键"的登记规则，禁止按字符串规范化判重；提供键族标注建议与 lint，防止将来再次被误合并（我方已踩过一次）。

### R4 图能力请给**算子支持矩阵**（支持 / 不支持 / 限制）

- `PgCteGraphStore` 为**只读**、多跳带深度上限与环检测。多跳路径、社区发现、写方法（`:12` 协议不暴露写）等均未承诺。
- **要求**：给出完整算子矩阵与限制条件。即便 CRM 当前不迁，也需据此评估 AGE → CTE 的可行边界，避免将来再出现"以为能迁、其实缺算子"的返工。

### R5 MCP transport：不要求实现，请给**接口规范**

- 贵方明示 transport 由消费方自实现、无排期 —— 我方接受。
- **要求**：请定义 transport 接口契约（方法签名、生命周期、错误语义），使 CRM 的自实现未来能**无成本回捐**为范式。

### R6 记忆层请成文 **fail-open / fail-closed 默认语义**

- `MEMORY_EXPERIMENTAL=True` 下，"维度不符 / 召回失败"应 fail-open 还是 fail-closed，目前无成文口径。
- CRM 侧多处 **fail-open 且静默**（正是 A3 要治的问题）。若底座给出纪律（如"维度不符必须显式报错 + trace"），CRM 可直接对齐，无需自行发明。

### R7 零残留词表请**版本化 + 发布机制**

- `tools/zero_residue.tokens` 已交付（522 B）。
- **要求**：加版本号与发布/同步机制（如随包发布、变更日志），避免两仓词表各自演进后漂移（同判据 #17 数据形态多副本）。

### R8 决策失败请提供**错误码分类法**以便对齐

- 我方 T0 将引入 `UNKNOWN_SCENARIO` / `DIM_MISMATCH` / `ENGINE_FAULT`。
- **要求**：贵方 `run_spine` 若已有失败分类，请公开其分类法；若无，建议共同约定一套。使未来若真迁移，错误语义不漂移。

## 5. 后续机制建议

1. **跨仓引用一律用 capability_id**（R1 落地后），`file:line` 仅作为"当次取证的辅助"，不作为契约。
2. **双向取证纪律**：任一侧引用对方结论前重跑 grep——本轮双方都栽在"复述旧锚点"。
3. **判据移植而非代码移植**作为长期机制：CRM 不迁 Python，但持续把贵方判据移植为 Node 等价件并做变异自证；贵方提供 R2 规格，我方回捐 Node 实现作为范式参考。
