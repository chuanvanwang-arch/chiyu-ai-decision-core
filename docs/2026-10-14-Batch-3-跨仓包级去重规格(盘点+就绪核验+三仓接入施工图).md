# Batch-3 跨仓包级去重规格（foundation 侧 · 2026-10-14）

> 范围：APS-ai-native / chiyu-enterprise / CRM-ai-native 对 foundation 已具备件的**包级去重**（设计文档 §六 Batch-3）。
> 纪律：本仓**不向三仓写任何产物**；本规格是给三仓的施工图，各仓自完成切换，每删一处跑一处 parity 守卫全绿即收口，**禁保留第二事实源**。
> 前置：Batch-2 全量就绪（T86/T88~T91）✅；foundation 34 capabilities 全 stable。
> 盘点方法：只读快照逐项定位（file:line 锚点可反证），按「A 纯重造可删 / B 域适配保留 / C foundation 缺口」分级。

## 一、盘点结论摘要

## 五、CRM 同步切消费方

CRM 是多数机制的上游源（Node 侧同构实现 + Python stdio 桥），Batch-3 对 CRM 的要求：

1. **parity 参照**：APS/enterprise 每项切换的对拍基准以 CRM 现有实现为准（如九尺子聚合、审批五态迁移、回流四通道）；CRM 侧 `test/calibration/parity.test.js`/`test/tier-predicate-parity.test.js` 等既有 parity 测试继续充当跨仓基准。
2. **协议对齐**（Python 内核边界，不 import）：monitorSubscriber.js/signalMetrics.js 等 Node 侧同构机制按 `contract/event.py` 字段口径对齐；两页（决策监控/智能体工作台）的域无关候选已并入 Batch-4/5 排期，不在本批。
3. **零动作项**：CRM 无需删本地件（它是源）；任一项 foundation 机制变更，CRM parity 测试即哨兵。

## 七、切换顺序与闸门（建议）

1. **第一波（A 类纯重造，先建守卫后删）**：APS A1~A5（connectors/promotion/reflux/feedback_loop/capability_audit——机制刚上迁、parity 锚点最新鲜）；enterprise E1（T86 修复的直接受益，收益高风险低）。

3. **第三波（回赠收口）**：enterprise E4（T93 已就绪）；E5 种子外置核查。
4. **闸门**：每项切换 = ① parity 守卫先绿后删 ② 该仓全量回归绿 ③ 在仓回函标注完成项；**禁保留第二事实源**（删而不切 = 断链，切而不删 = 双源）。
5. **依赖**：APS A8/A9 的对拍守卫依赖 foundation contract 闭集不变；若需增补闭集（如档位表/后端集），先回函 foundation 修订并同步 manifest，再切换。
