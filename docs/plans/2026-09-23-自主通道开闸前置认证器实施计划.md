## §0 定位（本组件解决什么）

2026-09-22 的 `平台自进化引擎实施计划` 已把 §12.3 七闸作为**机制**落地进 `chiyu_kernel`
（`evolution` 子包 + `orchestration.idem` + `audit.chain` + `state_machine` 熔断），
收口于 266 passed / 0 skipped。但 §12.3 还有一句**执行性**要求：

> 「七条正确性闸**全部必须先于自主通道上线**，任一缺失 ⇒ 自主通道不得开闸。」

即：机制建好 ≠ 能开闸。**缺的是一个把七闸 + 三条护栏串成"开闸前强制前置检查"的认证器**——
夜批调度器（下一轮）必须 `assert_channel_may_open()` 通过后才能跑。本计划交付的就是这个
认证器，**它只认证、不开闸**。

## §1 设计原则

1. **每个判据都有判别力（anti-fake-green）**：只查"模块存在"的探针是空跑。本认证器每个闸
   都注入一个"必红"的对抗输入（空样本 / 非白名单键 / 状态落库失败 / 篡改审计记录 / 红线命中 /
   空 scope 等）。若该机制对坏输入仍判绿，该闸判 RED——认证器本身也受判别力约束。
2. **认证器自身也须被反证**：`test` 必须把某个底层机制 monkeypatch 成失效，确认
   `assert_channel_may_open()` 转红——否则认证器是"永远绿"的假绿。
3. **不新增第二份判据表**：认证器只**引用**已落地的原语（`shadow_replay` / `KnobTable` /
   `apply_atomic` / `audit.chain` / `derive_idem_key` 等），不重写判据。
4. **零依赖、零 IO、零领域字面量**：纯函数 + 内存状态；不接 PG（无 PG 全绿）。
5. **阻断 vs 留痕分流**：`GATE_RED` 阻断开闸；`CHECK_NOTE` 是调度器/消费方接线项
   （如 budget_deadline 由夜批调度器注入，内核只提供熔断机制），不阻断但必须可见。

## §3 公开 API（`chiyu_kernel.evolution` 与 `chiyu_kernel.api` 同步暴露）

- `readiness_report() -> ReadinessReport`：跑全部 10 判据，返回结构化报告。
- `assert_channel_may_open() -> ReadinessReport`：任一阻断闸 RED ⇒ 抛 `ChannelNotReadyError(report)`。
- `ReadinessReport`：`checks` / `ready` / `blocking_red` / `summary()`。
- `CheckResult`：`check_id` / `title` / `status`(green|red|note) / `detail` / `discriminating`。
- `ChannelNotReadyError`：携带 `report`，错误信息列出所有 RED 判据。
