## 0. 一句话结论

CRM 与 foundation 之间的主要矛盾**不是"底座能力不足"，而是"语言边界 + 迁移 ROI 不成立"**。

- CRM 判定为 P0 阻断的 **F-02（AGE 图）前提已部分失效**：foundation 已 Ship `GraphStore` 协议 +
  `PgCteGraphStore`（纯 PG 递归 CTE、零新扩展），且 CRM 侧裸 `cypher` **已被收口在单一文件**
  （`src/decision/ageGraph.js`，6 处；依赖模块 12 个）。⇒ 图不再是"能不能迁"的第一闸门，
  **真实成本在 12 个依赖模块的图语义 + 61,135 行生产代码 + 785 个测试**，而非某个扩展。
- CRM 判定为 P0 的另一项 **F-01（记忆层 experimental）依然成立**，但它是"敢不敢把持久化写进硬验收"的问题，
  不是"能不能开工"的问题。
- 被列为 P1/P2 的 **F-04/F-05/F-06/F-07/F-08 在 foundation 侧已交付**（分别是 TenantProfile/DomainBundle/
  inject_domain、`register_scenario`+`ScenarioRegistryError`、门面覆盖检查 + 变异工具、
  `examples/reference_consumer` 1,079 行、零残留 lint 工具 + 词表）。**CRM 文档中的那些判断已过期。**

⇒ **结论：否决"以 foundation 为底座做 Python 全量重写"（选项 A）作为当前目标**，
改为 **"库内收敛（选项 B）+"**：把 foundation 已经成文的**判据**（而非 Python 代码）移植到 Node 侧，
让 CRM 的护栏达到与 foundation 同等的机械强度。CRM 真正要立即修的不是"键名没对齐"，而是**第 0 闸会把
未登记场景静默放行**（`src/config/configDecision.js:12-20`，本次核验新发现，CRM 自查未覆盖）。

## 3. 新增建议（Add）

### A1【最高收益】把 foundation F-05 的判据移植成 Node 侧 `DECISION_SCENARIOS` SSOT

- **为什么是最高收益**：这是唯一一条能同时闭合 C-01（键分裂）、U3（两库漂移）、并预防第 4 次同类事故的措施，
  且**完全不依赖 foundation**（Node 栈内即可做）。
- **三件套**：
  1. 常量注册表 `DECISION_SCENARIOS`：每键声明 `{ key, semantics, seeded, owner_module }`。
     ⚠ **`config_change` 与 `config-change` 必须登记为两个键**（`db/seed.sql:371` 已明文二者语义不同），
     **禁止"统一写法"式粗暴合并**——那会丢掉治理留痕语义。
  2. 守卫①（静态）：扫描代码中 `produceDecision(…)` / `requireDecision(…)` 的全部字面量键，
     ⇒ **未在注册表出现即红**（对齐 foundation `register_scenario` 的 fail-fast 语义）。
  3. 守卫②（跨环境）：对注册表全键做 **双库计数对拍**
     （本地便携 PG vs 生产库，仅只读查询），`行数差异 ⇒ 红`，消除"生产有、测试库没有"的环境维副本漂移。
- **验收判据（可证伪）**：从常量表删掉 `config-change` → 守卫①立即转红还原；
  在 `db/seed-decision-scenarios.sql` 补种 `llm-config-change` → 守卫②在两库都对拍通过。
  **变异自证必做**（否则守卫可能恒绿空跑）。

### A2【本次新发现】修复第 0 闸的假阴性：`configDecision.js` 的 catch 不能一律放行

- **现状**：`src/config/configDecision.js:12-20` try 调 `requireDecision`，catch 后落
  `recordDecisionEvent('config_change', …)` 并返回 `{ decisionId: null, ok: true }`。
  ⇒ **未登记场景、维度不合、内核异常，全部被压成同一个"成功"**（同 CRM 判据 #13「错误码压成一句」）。
- **建议**：catch 分支按 reason 分级——
  `未知场景` → 显式失败 + 带可判别 `reason`（禁止 `ok:true`）；
  `自治度不足/降级` → 才允许降级为事件，并留 `degraded: true` 痕迹。
- **验收判据**：投一个未登记的键 → 写操作返回可判别的失败 reason，且**不存在** `decisionId:null` 却 `ok:true` 的组合。

### A3 向量/embedding 单一事实源（消除三套并行维度判定）

- **现状**：1024 维在 `hooks.js:17/18/30`、`assembler.js:106/124/125`、`decisionRepo.js:158/159/245/331/665`
  各写一遍，且多处 fail-open（维度不符静默写 NULL / 禁用 L1）。
- **建议**：抽 `EMBED_DIM` 常量 + 统一 `assertVectorDim()`，三处改为同源调用；维度不符 = **显式错误 + trace 留痕**，禁止静默。
- **验收判据**：把 `EMBED_DIM` 改成 512 并跑写入路径 → 三处**都**报同一个可判别的错误；改回 1024 全绿。

### A4 MCP 暴露面咽喉加覆盖断言（防第 4 次漏注册）

- **现状**：`buildMcpTools`（`tools.js:45`）是唯一咽喉，但**没有任何断言**保证四支动作族都注册成功；
  历史已三次复发（discovery / connector / dealer），且 `server.js` 只 import 这一函数 ⇒ 独立 MCP 进程出错无人知。
- **建议**：在 `buildMcpTools` 末尾加 `EXPECTED_FAMILIES = ['discovery','connector','channel','dealer']` 覆盖断言，
  任一族工具数为 0 即 throw（带族名 reason）；**两个进程（app 进程 / 独立 MCP 进程）都要跑该断言**。
- **验收判据**：临时注释 `seedDealerActions()` → 断言转红（变异自证）。

### A5 HTTP 与 MCP 的授权判定同源（收敛判据 #15）

- **现状**：`src/mcp/` 对 `src/rbac.js` 引用 **= 0**；MCP 侧由 `gateway.js:284` 与 `intent.js` 按 per-Action
  `rbac_roles` 自判，而 `executor.js:91-96` 又判一次同款闸。
- **建议**：把角色决策收敛到 `rbac.js` 的 `can*` 纯函数（接收 `{actor,role,tenantId,scope}`），
  HTTP 与 MCP 两条通道**同源同码**；`mcp/auth.js` 保留为身份/scopes 解析层，不再承担角色决策。
- **验收判据**：parity 测试——同一 `{role, tenant, action}` 输入，两通道放行集必须**相等**（而非子集），任何一侧宽松即红。

## 4. 删除建议（Delete）

### D1 删除"Python 全量重写（选项 A）"作为待办目标
- **理由（量化）**：① 语言边界——消费 foundation 必须跨/或重写 Node；
  ② 61,135 行生产代码 + 785 个测试在线运行；③ AGE 语义承载在 12 个依赖模块，不是换扩展就能平移；
  ④ 图相关能力 foundation 只是"另一种实现"，不构成替换收益。
- **替代目标**：**契约对齐**（判据移植 + 守卫同强度），成本降低一个数量级且零停机风险。
- **纪律**：删除的是"目标"，不是"探索"——可在 `docs/` 归档决策记录（含否决依据），避免半年后重提案。

### D2 删除 F-02 作为"迁移可行性闸门"的定性
- foundation 已 Ship `PgCteGraphStore`（纯 PG 递归 CTE、零扩展）。改为**算子缺口清单**评估，不再作 Gate。

### D3 删除重复的播种副本之一（`db/seed.sql:231` 段）
- 两份播种 SQL 维护同一批键且已事实分叉（`integration-sync` 只存在于新文件）⇒ 必然继续漂移。
- ⚠ **纪律**：删除前确认 `seed-decision-scenarios.sql` 完整覆盖并含幂等 `ON CONFLICT (scenario_id, tenant_id) DO NOTHING`，

## 7. 对 CRM 自查结论的三条严谨化补刀

1. **"三态键分裂是拼写漂移" —— 不准确。**
   `db/seed-decision-scenarios.sql:175`、`db/seed.sql:371` 明文写着两者**语义不同、勿合并**。
   因此正确动作是"登记两个键 + 各自确权"，**不是"统一成连字符"**。真正的病灶是 SSOT 未覆盖 + 第 0 闸静默降级。

2. **"F-02 无 AGE 等价 = 最硬的一条阻断" —— 前提已部分失效。**
   foundation 已 Ship `PgCteGraphStore`（纯 PG 递归 CTE、零扩展依赖）；且 CRM 侧裸 cypher 只 6 行、
   集中在 `src/decision/ageGraph.js` 一个文件，属于**封装良好**而非散落耦合。迁移真成本在图语义与体量。

3. **"persist:false 同 enterprise 的 persist=None" —— 待复核，不宜并案。**
   `autonomyEngine.js:263` 注释自述该参数是"决策 id 尚不存在时，把落库延后到 createDecision 冻结"的阶段性选项，
   与 enterprise 全链路 `persist=None` 不落库不是同一形状。**建议先跑一次全链路追踪再定论**，避免按错 repaired 方案施工。
