## 0. 一句话

方案 A 的地基**已经存在**：`persist` 层的 `_store_write_edge` 就是"谓词参数化 + upsert + 全元数据"的受控边写原语，`PgCteGraphStore` 在同一张 `graph_edge` 表上只读派生——**写/读同表闭环，零新表、零新引擎**。方案 A 的实际工作量不是"造可写图"，而是三件收口事：把该原语从私有提升为受控 sanctioned 面、谓词闭集在写入端 fail-fast、单源裁定守卫白名单收窄。评估结论：**技术可行且成本低于 R9 文档原始估算**；建议维持排期（试点期出实现稿，1.0 后定夺）。

## 1. 取证更新（相对 R9 决策文档的三处修正/强化）

### 1.1 受控边写原语已存在（新发现，降低方案 A 成本估算）

`persist/__init__.py` 的 `_store_write_edge`（`PgVectorStorePersister` 内部工厂）实为通用受控边写原语：

| 能力 | 证据 |
|---|---|
| 谓词参数化 | `predicate` 为入参（非硬编码），与 layer/serves_dims/edge_source/evidence_ref/valid_from/valid_until/weight/relation_confidence 全元数据一同写入 |
| upsert 幂等 | `ON CONFLICT (from_id, to_id, predicate) DO UPDATE SET ...`——重放同边更新元数据，不产生重复行 |
| 单表落点 | `graph_edge`（三表唯一事实源之一），与 `PgCteGraphStore` 读侧同源 |

**推论**：R9 决策 §3 对方案 A"需定义顶点写语义 / 只支持有向建边"的成本判断偏保守——边写半边的底座实现**已在树内且被 `write_decision_memory_net` 生产使用**（真库 E2E 已守护，T43）。方案 A 剩余工作见 §3。

### 1.2 谓词闭集为七边，非六边（勘误）

R9 决策 §1 写"6 类边"，实为**七边**：`contract/particle.py` `MEMORY_PREDICATES` 七个 `PredicateSpec`（M 层，source=engine）：`DECIDED_ON / REFERENCED_PRECEDENT / DERIVED_FROM_EXCEPTION / ESTABLISHES_FRAME / OVERRIDES / CAUSED / INFLUENCED`。与 CRM `ageGraph.js` 边型逐字一致（consumability-design 实锤）。CRM 依赖的边型**全部**在既有闭集内，无需扩词表。

### 1.3 单源纪律本就允许两个 sanctioned 写者（口径澄清）

`graph/__init__.py` 模块纪律明文："写边一律走 `persist.write_decision_memory_net` / `ontology.OntologyGraph`"——单源指**同一张表的落点唯一**（graph_edge 只经 persist 层落库），不是"全仓只许一个写函数"。T44 守卫的裁定面（`graph_edge` 直写仅限 `persist/__init__.py`）与该口径一致。方案 A 在 persist 包内**新增一个受控写入口**不破单源，只需守卫白名单同步（§3.3）。

## 2. 方案 A 草案：受控写谓词闭集

### 2.1 闭集定义（M+K 合并视图，复用既有机制）

写入端受理的谓词闭集 = `profile.predicates` 的合并视图（`PredicateSet.memory` 七边 + `PredicateSet.knowledge` K 层，消费方注入）——**与 `OntologyGraph.link` 同一闭集来源**，不在本草案新造词表：

| 项 | 值 |
|---|---|
| M 层（内核常量） | `MEMORY_PREDICATES` 七边 |
| K 层（消费方注入） | `profile.predicates.knowledge`，随租户 profile 走 |
| 未受控谓词 | **fail-fast 抛**（与 `link` 同纪律：有界谓词，不静默） |
| 层校验 | 构造期强制（`PredicateSet.__post_init__` 已有：M/K 层标记错即红） |

### 2.2 API 草案（示意，非最终签名）

```
persist.write_controlled_edges(store, edges, *, profile) -> WriteReport
  edges: [{from_id, to_id, predicate, layer, evidence_ref, valid_from,
           valid_until, weight, confidence, serves_dims, edge_source}]
  判据：
  1. predicate ∈ profile.predicates（M∪K），未受控即抛（写入端 fail-fast）
  2. from_id/to_id 必须指向已存在的 particle（外键/预检，防悬空边——
     这是与 CRM ageGraph 的关键差异：AGE 的 MERGE 会隐式建顶点，
     受控写**不隐式建**，顶点必须经粒子写显式落库，见 §2.3）
  3. 落 graph_edge（upsert 语义同 _store_write_edge），写事件留痕
```

### 2.3 顶点写：明确**不提供**（方案 A 的纵切边界）

CRM `ageGraph` 的 `addDecision`（7 字段顶点）与 `addParticleVertex` 在方案 A 下的**正确归宿是粒子写而非图写**：决策顶点=decision 粒子（persist 已写），实体顶点=对应 type 粒子（`particle` 表）。图写只认 `particle_id` 引用，**不隐式建顶点**——这保留了"particle+graph_edge+event 三表是唯一事实源、图只是派生视图"的定位（`graph/__init__.py` 模块纪律），也正是方案 A 与方案 B（`WritableGraph` 全协议）的本质分界：**A = 边写受控原语；B = 顶点+边的第二存储语义（破单源，须 deprecation 裁定）**。

对 CRM 的含义：迁到方案 A 后，`ageGraph` 的 `addEdge` 三函数退役；`addDecision`/`addParticleVertex` 改走粒子落库（底座 `PgVectorStorePersister.persist` 语义），`MERGE` 的隐式建点行为被"顶点必须显式落库"取代——**多一步显式，换单源可审计**。

### 2.4 CRM 边属性映射

| CRM ageGraph | 方案 A 落点 |
|---|---|
| `SET r.edge_ts` | `valid_from`（业务时钟；双时钟纪律沿用 `contract/memory.py`） |
| 边上的 `kind` | `predicate`（闭集内） |
| 证据/来源留痕 | `evidence_ref` / `edge_source`（engine=脊柱写；consumer=消费方回填，闭集校验同谓词） |
| 权重/置信 | `weight` / `relation_confidence` |

## 3. 实现收口清单（试点期执行，预估三件）

1. **原语提升**：`_store_write_edge` 工厂抽到 `persist/graph_edges.py`（`write_decision_memory_net` 与新受控写入口共用同一落库函数，包内不出现第二份 INSERT INTO graph_edge）；sanctioned 面登记 + 门面同步（走 T40–T44 已验证的"新增子包四步"纪律）。
2. **守卫白名单收窄**：`tools/check_single_source_memory.py` 的 `graph_edge` 白名单从 `persist/__init__.py` 改为 `persist/graph_edges.py`（一个文件、一份 SQL——单源在文件粒度可机检）。
3. **判据落地**：写入端闭集 fail-fast / 悬空边拒绝 / upsert 幂等 三判据 + 变异自证（沿 T40–T44 体例）；`@pytest.mark.pg` 真库 E2E：受控写→`PgCteGraphStore` 读回（写读同表闭环判据）。

**不做的**：不动 `GraphStore` 只读协议（消费方零感知）；不新增 capability 层（属 `persist` 层扩展，无新 LAYERS 登记）；manifest 口径 1.0 前维持"写能力未提供"，实现稿就绪后随试点结果更新。

## 4. 准入四前提评估（底座补充的扳机判据）

| 前提 | 评估 | 依据 |
|---|---|---|
| ① 域无关 | **满足** | 七边谓词是底座 L0 词表（`contract/particle.py:123`"跨域通用"），非 CRM 发明；APS 决策回链、enterprise 审计链同词表 |
| ② 足够 stable 可冻结 | **试点期验证项** | upsert 语义与列集已在生产路径（`write_decision_memory_net`）跑通且有真库 E2E；待试点验证的是"消费方直接调用受控写入口"这一新用法面 |
| ③ 不破单源 | **满足** | 同表、同落库函数、同事务边界；守卫白名单文件粒度收窄后**强于**现状 |
| ④ 惠及 ≥2 消费方 | **满足** | CRM（试点排除面撤销的通路）；APS（决策依赖边落底座，替代自建）；enterprise（审计回链复用） |

四前提全过——方案 A 是合格的"底座补充候选"，与 A6 记忆毕业同模式：**通用资产 + 工程收口，不是领域特供**。

## 5. 风险与非目标

- **非 AGE**：不提供 Cypher/MERGE 隐式建点；任意 label 顶点写不支持（粒子 substrate 之外）。
- **双时钟纪律**：`edge_ts` 一律映射业务时钟字段，禁用落库时钟冒充决策时间（沿用专利族 H 判据）。
- **不要为 A 抢跑 B**：`WritableGraph`（顶点+边第二存储）仍按 R9 排期留待 1.0 后裁定；若试点证明粒子写路径已覆盖顶点需求，B 可能**永久不需要**——这是本草案最希望的结局。
- **0.1.0 冻结不破**：本草案只是设计与判据，0.1.0 冻结面（manifest"写能力未提供"）一字不动。
