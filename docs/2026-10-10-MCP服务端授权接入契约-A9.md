## 0. 一句话

底座 `McpServer` 给的是**授权机制**（零信任默认拒绝 + 可插拔 `auth` 判定钩子 + 写操作两阶段确认），**授权策略**（谁能调什么）是消费方资产——CRM 的 `rbac.js`（`CORE_ROLES` + per-Action `rbac_roles` 的 `can*` 纯函数）就是策略本体。本契约把注入面写成语言无关规格：CRM 把 `can*` 适配成 `auth(ctx)` 注入即闭合 A9，底座零改动。

**机制/策略分界（为什么底座不内置 RBAC）**：底座吸进销售域角色字面量 = 违反零领域字面量铁律，且摧毁多消费方复用（APS/enterprise 的授权模型各异）。机制一次做成，策略每家自带——这与 R5"协议底座给、transport 消费方实现"同构。

## 1. `auth` 钩子契约（判定面）

`McpServer` 构造期注入 `auth`（真值来源 `McpServer.__init__`）：

| 要素 | 契约 |
|---|---|
| 签名 | `auth(ctx) -> bool`；`ctx` 为 `Mapping[str, Any]`（见 §2） |
| 缺省语义 | **未注入 ⇒ 一律拒绝**（`AuthDenied`）。零信任：默认拒绝，非默认放行 |
| 调用时机 | 每次 `tools/call`，在**工具存在性校验之后、两阶段确认之前**（顺序：未暴露工具先报 `ToolNotExposed`，再鉴权，再确认） |
| 调用频率 | 每次调用都判（无缓存承诺）；实现方可自行缓存但**必须以 ctx 为键** |
| 纯度要求 | `auth` 应为**判定纯函数**：只读 ctx、无副作用、不抛（抛出按拒绝处理并由服务端转 `AuthDenied` 语义——实现方不应依赖抛错传信） |
| 返回语义 | `True`=放行（进入后续风险分级/确认流程）；`False`=拒绝（`AuthDenied`） |

底座内置的唯一参考实现：`allow_principals(*names)` 白名单（`ctx['principal']` 命中才放行）。CRM 的 RBAC、APS 的角色矩阵、enterprise 的审批态门控，都是**同一位形空间的不同策略**，均按本节签名注入。

## 2. `ctx` 契约（调用方身份如何进来）

`ctx` 由**传输层/宿主**在每次请求时构造，`handle_request(req, ctx=...)` 直通给 `auth` 与工具 handler：

| 键 | 必填 | 语义 |
|---|---|---|
| `principal` | 建议（两阶段确认强依赖） | 调用主体标识。缺省按空串 `""` 参与令牌绑定（§3）——**意味着换主体 ≠ 旧令牌仍可用，但空主体令牌不可区分主体**，生产宿主必须注入真实 principal |
| 其他键 | 自由 | ctx 是开放 Mapping：CRM 可放 `roles` / `tenant_id` / `session_id`，`auth` 闭包按需读取；底座**不解释、不白名单化** ctx 键（机制不认识策略词汇） |

**传输无关**：stdio 路径由 `StdioTransport(server, ctx=...)` 统一注入；HTTP 路径由 CRM 的 Express 中间件从 session 解出身份后构造 ctx 喂 `handle_request`。底座不接触 cookie/token/网络——身份解析永远在宿主。

## 3. 两阶段确认契约（write 工具）

工具经 `expose(name, handler, risk="write", ...)` 登记为写类后，调用走两阶段：

```
第一次调用（无 confirm_token）
  → 返回 {status: "confirmation_required", confirm_token, summary}   ← 不是错误
第二次调用（带同一 confirm_token，参数与主体不变）
  → 真正执行 handler(args, ctx=ctx)
```

**令牌规格**（真值来源 `issue_confirm_token` / `verify_confirm_token` / `canonical_args`）：

| 要素 | 契约 |
|---|---|
| 算法 | `HMAC-SHA256(secret, "{name}|{canonical_args}|{principal}")`，hex 编码 |
| `canonical_args` | JSON 序列化：键排序 + 紧凑分隔符 + `ensure_ascii=False`；同语义参数必得同一串（跨语言实现必须逐字节对齐此规范化，否则 Python 签发 / Node 验签会互不认账） |
| 绑定三元组 | 工具名 / 规范化参数 / 主体——**任一变更 ⇒ 验签失败**（`ConfirmTokenInvalid`），防"拿 token 再改参数"重放 |
| 比较方式 | 恒定时间比较（防计时侧信道）；Node 侧等价物用 `crypto.timingSafeEqual` |
| `secret` 生命周期 | 未注入 ⇒ 进程内随机 32 字节 hex（**重启即失效，不跨进程重放**——这是有意设计：确认意图不该活过进程）；注入 ⇒ 消费方自管轮换 |
| 与零信任写入的关系 | CRM 现行"本地签发 MCP token + confirm_token 两阶段"流程与本节**同构**：CRM 侧已有的签发/验证逻辑只需对齐 §3 规范化与绑定三元组，即可把底层实现换成 `McpServer` 内建（或反向：CRM 保留自身实现，仅需满足本节语义判据） |

## 4. 错误语义（语言无关，机器可路由）

| 异常 | 触发 | JSON-RPC 表现 |
|---|---|---|
| `ToolNotExposed` | 调用未注册工具（不静默放行） | `error.code=-32000`，消息含已暴露清单 |
| `AuthDenied` | `auth` 未注入 / 返回 False / 抛异常 | `error.code=-32000` |
| `ConfirmRequired` | **write 工具第一阶段**——不是错误，是待确认结果 | `result.status="confirmation_required"` + `confirm_token` |
| `ConfirmTokenInvalid` | 令牌无效/被篡改/主体不符 | `error.code=-32000` |
| 未知 method | 非 `tools/list` / `tools/call` | `error.code=-32601` |
| JSON 解析失败（stdio） | 行非合法 JSON | `error.code=-32700` |

铁律：**错误不静默**。任何分支不得返回伪造成功；鉴权失败的响应不得泄露"哪个工具存在"以外的新信息（`ToolNotExposed` 先于 `AuthDenied` 是有意序——工具清单非机密，但判定顺序消费方不得自行调换后宣称兼容）。

## 5. CRM（Node）接入与回捐验收

### 5.1 接入路径（三步，底座零改动）

1. **策略适配**：`rbac.js` 的 `can*(role, action)` 纯函数包一层 `auth(ctx)`：`ctx.roles` / `ctx.principal` → 对当前目标 Action 判定 → `bool`。
2. **宿主构造 ctx**：Express 中间件从 session 解出 `principal` + `roles`，喂 `handle_request(req, ctx)`。
3. **写工具两阶段**：前端收到 `confirmation_required` 后二次提交带 `confirm_token`；CRM 现行零信任两阶段流程语义不变。

### 5.2 回捐验收判据（满足即确认"A9 闭合"）

1. `auth` 签名/时机/纯度符合 §1（含：未注入时默认拒绝这一条由**底座守卫**保证，CRM 侧 E2E 须有一例"无 auth ⇒ AuthDenied"）；
2. `canonical_args` 规范化与 §3 逐字节一致（跨语言对拍：同一组参数在 Python `canonical_args` 与 Node 等价函数产出相同字符串）；
3. 绑定三元组变异测试：改参数 / 换主体 / 换工具名 ⇒ 令牌失效三例全红；
4. 错误语义对 §4 表（特别是 `ConfirmRequired` 走 `result` 而非 `error`）；
5. E2E：白名单内主体 read 直通 / write 两阶段闭环 / 白名单外主体 `AuthDenied`，全程记录留档。

> 回捐形态：`auth` 适配层 + `canonical_args` 等价件 + E2E 测试记录。底座侧复核以本文档 §1/§3/§4 为准，不逐行对拍代码。
