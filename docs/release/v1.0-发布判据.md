# foundation v1.0 发布判据

> 定位：本文件是 v0.1.0 → v1.0.0 的**正式发布闸**。任何一项未满足，不得打 `v1.0.0` tag。
> 语义：semver 之下 1.0 = **sanctioned 面冻结承诺 + 生产级可信**。本判据回答"凭什么敢承诺"。

## §0 版本口径

| 元素 | 0.1 时点 | 1.0 要求 |
|---|---|---|
| 分发包版本 `__version__` | 0.1.0 | 1.0.0（两包同步） |
| 门面版本 `API_VERSION` | 1.0.0（已先行） | 与分发包对齐 |
| 契约版本 `CONTRACT_VERSION` | 在册 | 不变（契约未破坏） |
| 能力清单 | 29 项：27 stable + 2 experimental | **stable 集合冻结**，experimental 集合不变或缩小 |

## §1 A 类：承诺收口（工程动作，发布前必须全部完成）

- [x] **stable 集合冻结**：`version.CAPABILITIES` 中全部 stable 层宣布 1.0 兼容（声明落于 `version.py` 模块头 + `CHANGELOG [0.1.0]` 兼容性声明 + manifest `compatibility_notes`）；此后 BREAKING 必须先走完整 deprecation 周期（先 warn 一版再移除）。
- [x] **experimental 划界**：`memory` / `evolution` 保持 experimental，**明确排除出 1.0 兼容承诺**，写进 `contract/capability-manifest.json`（`compatibility_notes`）与发布说明 §五。
- [x] **接口参考核对**：2026-10-09 机械比对门面 `__all__`（kernel 380 符号全覆盖；decision 补齐 `DecisionError` / `DECISION_ERROR_CODES` 两符号并修正计数 12→14）。1.0 发布前按 §4 再再生一次并核对。
- [x] **`git tag v0.1.0`** 补打（tag 于 T31=1350f42，含内核抽取全部内容，为升级演练真实起点）。
- [x] **CHANGELOG 启用**：`[Unreleased]` 历史内容经 tag 实证已随 `v0.1.0` 发布，并入 `[0.1.0]`（含 compatibility 声明）；`[Unreleased]` 留空节承接生产窗口期变更，1.0 发布时转入 `[1.0.0]`。

## §2 B 类：生产实证（硬门槛，日历约束，不可用工程动作替代）

四样证据，缺一不发版：

1. **接入回执**：≥2 个消费方完成 wheel 化接入并存档回执于本仓 `docs/`（import 面清单 + `require_capabilities` 断言通过记录）。
   - ⛔ 接入必须走 wheel + sanctioned 面；任何内部路径消费（如 `chiyu_kernel.store.pg_store`）的证据**无效**。
   - 消费方接入时自跑 `tools/check_import_surface.py`（门禁对消费方 import 面同样可执行）。
   - 进度（2026-10-09）：**APS 回执已收（1/2）**，见《接入回执-APS-2026-10-09.md》；enterprise / CRM 待回。
2. **真实负载运行台账（暴露量导向，2026-10-09 修订）**：≥1 个消费方（建议 CRM 生产环境）在**真实负载 + 真库**下运行，**同时满足**以下四项：
   - **暴露量**：累计真实决策落库 ≥ **N 次**（N 待 CRM 首周实测标定；标定前按日历兜底执行）；
   - **业务周期覆盖**：覆盖 ≥1 个完整业务周期（含一次月末/周批处理——周期性任务本身是日历事件，此项为物理约束，不可用次数替代）；
   - **真实升级**：窗口内 ≥1 次 0.1.x → 0.1.y 真实升级演练（检验 CHANGELOG / deprecation / 兼容性断言链路）；
   - **P0/P1 缺陷清零**（P0 定义见 SLA 文档；出现即修复并重新累计）。
   - **日历兜底**：消费方无法统计暴露量时，退回「连续运行 ≥4 周」。
   - ⚠ 修订动因：日历是暴露量的**代理变量**——低负载环境（如测试环境真跑）按日历空转无意义；原「日历 ≥4 周」条款将代理变量写成了目的。长周期失效模式（泄漏/膨胀/慢查询劣化/锁竞争）由暴露量 + 业务周期覆盖共同兜住，不因修订而失防。
   - 进度（2026-10-09）：APS 侧窗口已开启（起算 2026-10-09，测试环境真跑，暴露量统计待其探针补齐）；其台账"起算=终点同日收口"的主张**不采信**——修订前后均不成立：暴露量 0 次累计、业务周期 0 个覆盖。
3. **真库 E2E 沉淀**：运行窗口内发现的真库场景，固化为 `@pytest.mark.pg` 标记用例回流本仓测试套件（至少覆盖：三表落库读回、零硬删除拦截、图视图派生）。
4. **SLO 实测**：采集 SLO 实测数据回填 `docs/release/v0.1.0-SLA与支持承诺.md` 的 SLO 建议表（至少：spine 决策延迟、persister 吞吐、图查询深度时延）。（升级演练已归并至 §2-2 第三目，此处不再单列。）
   - 进度（2026-10-09）：SLO 已获 APS 单机基线并回填 SLA §三（spine 全链 p50≈51.5ms / 吞吐 ≈15.6 决策/秒 / 图查 p50≈1.57ms）；生产宿主 + 并发负载重采 ⬜ 窗口内完成。

## §3 C 类：支持与安全

- [ ] SLA 承诺的响应通道**实际可运行**（issue 入口、回执流程、升级联系人，非文档承诺）。
- [ ] 安全自查一轮：DSN 处理、MCP confirm token、SQL 注入面、零硬删除在真库上验证（§2-3 的真库 E2E 覆盖）。
- [ ] 独立安全审计（有条件则做；无条件则记为 1.0.x 债务并对外披露）。

## §4 发布操作序列（判据满足后）

1. 重生成接口参考 + capability manifest，四道 lint 门禁 + 全量回归绿；
2. `CHANGELOG` 定稿 `[1.0.0]`；两包版本号 → 1.0.0；重构建双 wheel 并核对包内容；
3. clean-room 冒烟：新 venv 安装双 wheel + `require_capabilities([...])`；
4. `git commit` + `git tag v1.0.0`；向各消费方发 1.0 回执。

## §5 判定速查

| 问题 | 判据 |
|---|---|
| 何时可打 v1.0.0？ | §1 全勾 + §2 四证齐 |
| 最短日历时间？ | 暴露量达标即发版——下限 = 覆盖 1 个完整业务周期（含月末/周批，约 2–4 周视业务周期而定）；暴露量无法统计时日历兜底 ≥4 周。A 类已收口（2026-10-09），与窗口并行 |
| 谁是主证据源？ | CRM 生产（最强）；APS 真跑次之；enterprise clean-room 接入再次 |
| 什么情况延期？ | 暴露量累计期间出现 P0/P1 → 修复后暴露量**重新累计**（业务周期覆盖同理） |
