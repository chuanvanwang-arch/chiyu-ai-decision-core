## 2. 🔴 质量问题：v0.1.0 wheel 为"中间态"构建

### 2.1 证据链（全部实拍）

| 证据 | 值 | 结论 |
|---|---|---|
| `chiyu-kernel` wheel 构建时间戳 | `2026-10-09 09:19:59` | |
| kernel 源码 `scenario/registry.py` 最后修改 | `2026-10-09 09:31:01` | **晚于 wheel 构建 11 分钟** |
| wheel 内 `api.py` 是否含 `set_key_format` | ❌ **False** | 源码 `api.py` 有 3 处引用 |
| wheel 内 `api.py` 是否含 `capabilities` / `DecisionScenarioProfile` | ✅ True | 见下（中间态定位） |
| `chiyu-decision` wheel 是否含 `errors.py` | ❌ **False**（仅 13 文件） | R8 的 `DecisionError` 缺失 |
| 发布说明声称 | 含 `set_key_format`、`DecisionError` 四码、`resume_spine`、`McpServer` 等 | |

### 2.2 根因与定性

`v0.1.0` tag 打于各功能**实现提交之后**，但 **wheel 未在最终源码上重新构建**——它的内容点是 **R1（capabilities）之后、R3（set_key_format）/R8（DecisionError）之前**的中间提交快照（因为 wheel 里 `capabilities`/`DecisionScenarioProfile` 有，而 `set_key_format`/`errors.py` 没有）。

**这直接违背贵方 v1.0 判据的两条 A 类承诺**：
- §1「stable 集合冻结」——消费方拿到的 sanctioned 面并不完整；
- §1「接口参考由门面 `__all__` **机械生成**」——当前 wheel 与发布说明不一致，说明机械生成未覆盖 wheel 构建环节。

### 2.3 对 foundation 的三条修复要求

1. **以最终源码重新构建双 wheel**，确保 wheel 内 `api.py`/`errors.py` 与发布说明一致；
2. **在构建流程加"wheel 内 `__all__` 与源码门面一致性"门禁**（对比 wheel 解包后的 `__all__` 与源码 `__all__`，不一致即红），防止再次"中间态发版"；
3. **发布说明补充 sanctioned 面函数真实签名**（当前 `register_scenario` 等无签名，消费方只能 `inspect`——实测签名为 `(key, *, title, description='', version='0.1.0', rubric='', redline='', inputs=(), outputs=(), required_gates=())`）。

## 3. 未决硬阻塞重申：图写（R9）

我方迁移方案 Part A 的差异表显示，**CRM 的图是"可写"的**：

```js
// src/decision/ageGraph.js:95-96 / :124 / :149-152
MERGE (n:Decision {decision_id:$decision_id}) SET n.scenario_id=...
MERGE (a)-[r:{rel} {kind:$kind}]->(b) SET r.edge_ts=$edge_ts ...
```

而贵方 `GraphStore` 协议是**只读、无写方法**（`contract/capability-manifest.json` 亦未列图写能力）。这承载 CRM **12 个依赖模块**的派生关系，无法用只读协议承载。

**请求**：在 capability manifest 中明确图写能力状态，并给出排期或替代方案（受控可写谓词集合 / 写接口 / 消费方自建 + 纳入 sanctioned 面）。**R9 未决前，我方 P1 试点不会启动。**
