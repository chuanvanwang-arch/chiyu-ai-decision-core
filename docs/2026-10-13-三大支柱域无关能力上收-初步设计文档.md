# 三大支柱「领域无关能力」上收 —— 最终方案（合并三仓盘点 + CRM 两页测绘）

> **文档性质**：最终方案（consolidated final plan，升级自"初步设计文档"）。
> - 上游①：foundation 审计 + 原《三大支柱域无关能力上收-初步设计文档》（CRM 回捐 + 八闸更正 + P0→P3）。
> - 上游②：CRM 两页测绘《CRM两页(决策监控+智能体工作台)域无关能力上收分析》（2026-10-14，可观测底座 + agent 运行时 + 调度）。
> - 上游③（本次新增，三仓各自盘点）：enterprise《企业仓底座能力盘点与迁移梳理》(185 文件→4 类) / APS《APS 底座能力盘点与迁移边界梳理》(94 模块→A/B/C 三档) / CRM《crm-底座能力盘点与迁移账》(56 上收 + 12 留)。
> - 触发：用户战略指令——优秀做法全收敛 foundation 成基座能力、可复用于三仓及未来项目；验收 = APS/enterprise 在三大支柱达 CRM 同等层级；且"两页内容都需考虑收敛 foundation"。
>
> **本方案定位**：把「审计 + 三仓盘点 + 两页测绘」合为**统一能力盘点 → 收敛动作映射 → 统一分批排期**的可评审、可落地最终方案。

## 〇、判定校准（诚实陈述，trust-but-verify）

1. **三仓盘点交汇，方向修正为"双向 + 三仓"**：原假设「CRM 首个落地、foundation 收敛不全面、从 CRM 单向 harvest」被三仓盘点修正——APS（94 模块）、enterprise（185 文件）、CRM（56 项）三大支柱能力**高度同构**，验收标准基本满足。真正风险是**「三仓各自造同构域无关机制 → 分叉成第二事实源」**。故收敛 = ① 三仓双向去重（改消费 foundation）；② 补三仓共有缺口；③ **补 foundation 自身缺口**（契约面 + 一处真 bug）。
2. **栈无关是硬约束**：三仓栈不同（CRM Node / APS Python / enterprise Python）→ 上收机制必须是 L0 契约 + 纯函数机制，否则无法跨仓复用。
3. **两页测绘印证用户点名**：决策监控 = 可观测底座（点名①）；智能体工作台 = agent 运行时 + 调度（点名①③）。二者**绝大多数域无关**（仅销售七阶段闸门/七维/8 销售智能体语义/lead-fit 评分/业务定时器名留 CRM）。
4. **foundation 自身缺口被两盘点显式暴露**：APS 报 GAP-1~5（events/context/embedding/llm/orchestration 有 impl 无 sanctioned 契约面，消费方被迫 import 内部路径）+ GAP-6~9（feedback_loop/capability_audit/connectors/知识升格回流管道缺失）；enterprise 报 `chiyu_kernel/store` **不看 schema（进程单例会串库）** 的真 bug。这些是消费方去重切换的**前提**，须先修。

## 一、上收总原则（边界纪律，升级版）

1. **机制回捐、域值留消费方**：foundation 只吸纳机制原语/状态机/算法/编排范式；域取值（粒子类型/本体/场景名/闸名/agent 名/任务名/评分维度）由各消费方按领域注入。对齐「内核零领域字面量」。
2. **契约先行、机制随后**：`contract.*` 的 D1–D8 词汇保留为单一事实源；新增件先落 L0 契约再落机制；经 sanctioned 门面（`chiyu_kernel.api` / `chiyu_kernel.contract` / `chiyu_kernel.approval` / `chiyu_decision.api` / `chiyu_portal.api`）re-export。
3. **foundation 自身缺口先行**：消费方去重切换前，foundation 须先补齐 GAP-1~5 契约面 + 修 `store` schema bug，否则消费方无处可切（只能继续 import 内部路径，违反 sanctioned 面纪律）。
4. **三仓双向去重，禁第二事实源**：三仓对 foundation 已有同名能力的本地再实现（host/scenario/decision/connector/memory/llm/ontology/approval/tenant…），迁移首选「改消费 foundation + 删本地重造」，不是整目录复制。
5. **fail-closed 铁律**：所有安全/决策闸默认拒绝；自进化「无 HITL 绝不生效、绝不自动 apply」。
6. **栈无关**：L0 契约零依赖、机制纯函数；持久化/IO 留消费方（G-零IO）。
7. **脱域三铁律为每批 acceptance**：G-域无关（内核符号 grep 禁域字面量）/ G-零IO / G-对等可测（parity 清单 + parity 守卫含变异自证）。
8. **横性要求**：每批落定向 CRM/APS/enterprise 三仓发函；CRM 核收（仿 T79 整盘核收）。

## 三、foundation 自身缺口（消费方去重的前提，独立优先）

> 两盘点显式暴露的 foundation 侧工作，与"从消费方 harvest"正交，须**先于**跨仓包级去重完成。

1. **契约面缺口 GAP-1~5（impl 无 sanctioned contract）**：`events`/`context`/`embedding/vector`/`llm`/`orchestration` 目前只有内部实现，无 `chiyu_kernel.contract` 契约面 → 消费方（APS/enterprise）被迫 import 内部路径，违反 sanctioned 面纪律。须逐项补 `contract/event.py` / `contract/context.py` / `contract/vector.py` / `contract/llm.py` / `contract/orchestration.py`，并经 `api.py` re-export。
2. **`chiyu_kernel/store` schema 感知 bug（真 bug，非 harvest）**：enterprise `tenant/store.py` 自建 `(profile,schema)` 双键隔离的**根因**是 foundation `open_store` 不看 schema、进程单例会串库。须修 foundation `store` 使其 schema 感知，而非保留企业副本。
3. **能力缺失 GAP-6~9**：`feedback_loop` / `capability_audit` / 通用 `connectors` 框架 / 知识升格回流管道（`promotion`/`reflux` 机制抽象）——APS/enterprise 有参考实现，foundation 缺，须上迁。
