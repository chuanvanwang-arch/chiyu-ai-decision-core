# CRM 两页（决策监控 + 智能体工作台）域无关能力上收分析（致用户 / 三仓）

> 触发：用户指令——`sales-decision-monitor`、`agent-workbench` 两生产页面"里面有很多内容，都需要考虑收敛到 foundation"。
> 方法：两页均为登录墙后 SPA，WebFetch 仅取到登录壳；按 trust-but-verify 改读 CRM 前端
>       源码真值（`/d/system/CRM-ai-native`），由 Explore 子代理只读测绘（file:line 锚点，
>       零代码变更）。本分析据此逐项分类「域无关（→foundation）vs 域特定（留 CRM）」。
> 纪律：本仓严禁向三仓写产物；上收 = 把域无关机制搬进 foundation，域语义留消费方。

---

## 〇、一句话结论

两页暴露的**几乎全是通用 AI 系统底座**，而非 CRM 业务：可观测底座（失败不静默）、根因归因、
信号链路、参数处方、事件总线、agent 编排+可解释、契约合规矩阵、定时调度、影子重放、自进化闭环。
**仅 5 类语义填充属 CRM 域特定**（销售七阶段闸门、七维概念、8 个销售智能体行为、lead-fit 评分、
业务定时器名）。这印证用户战略「优秀做法全收敛 foundation 成基座能力」——这两页正是此前
Batch 计划**未充分覆盖**的「监控底座」与「agent 运行时」两大块，须补入收敛计划。

## 五、边界纪律（重申 + 本批新增）

- ⛔ 本仓严禁向 CRM/APS/enterprise 写产物；上收是把域无关机制搬进 foundation，域语义留消费方。
- ⛔ 域特定（留 CRM，绝不上收）：销售七阶段闸门名（A16/A17）、七维概念维（A19）、8 个销售智能体语义（B11）、lead-fit 评分维度（B22）、业务定时器名（B24 内 crm-risk/sales-daily/named-visit 等）。
- ⛔ 改 foundation src 须用户逐批明确授权；每批落地须变异自证 + 组合全量回归 + 门面/能力登记同步。
- **零领域字面量铁律**：foundation 子包不得出现 CRM/APS/enterprise 字面量（grep 守卫）；域闸名/agent 名/任务名由消费方注入。
- **UI 组件库边界（新增，需用户裁定）**：S03 schema 受控渲染、SSE 实时浮卡、cytoscape 可审计图谱、七视角待办——这些是**前端通用范式**。foundation 当前是 Python 内核（chiyu_kernel/chiyu_decision/chiyu_cli），不含前端。两种处置：
  (a) **仅上收数据契约 + 渲染协议**（foundation 定义 schema 形状/事件协议，前端组件留消费方复用）—— 推荐，守 foundation 后端定位；
  (b) 另立前端组件库（超出 foundation 范围，建议交消费方或独立 UI 仓）。
  **默认按 (a)**：foundation 收「S03 schema 字段契约 / SSE 事件协议 / 图谱节点边契约」，不收 React/Vue 组件本身。
