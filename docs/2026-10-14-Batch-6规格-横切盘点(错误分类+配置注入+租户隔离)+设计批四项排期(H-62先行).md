## 二、横切盘点一：错误分类

### 2.1 现状（证据链）

- **门面已逐个 re-export 约 30 个错误类**（`api.py:47–947` 段逐项 import 并登记 `__all__`），消费方可见；但**无统一基类、无码表**。
- **决策层已先行收敛为闭集码表**：`chiyu_decision/errors.py` 定义 `DecisionError(Exception)` + `DECISION_ERROR_CODES = {ENGINE_FAULT, UNKNOWN_SCENARIO, DIM_MISMATCH, CONTRACT_VIOLATION}`（`errors.py:23–39`），`code` 为机器可路由字段，消费方按 `code` 路由、禁按 message 匹配——并明言要消灭泛型 `ValueError`。
- **契约层（contract/*）绝大多数错误类仍继承 `ValueError`**：`QuotaGateError`/`ApprovalEngineError`/`SchedulerError`/`NightlyReportError`/`ObservabilityError`/`AbExperimentError`/`AssembleError`/`AgentRuntimeError`/`GateChainError`/`AttributionError`/`Audit4QError`/`CapabilityAuditError`/`FeedbackTemplateError`/`CalibrationStateError`/`ExpressionError`/`PromotionPolicyError`/`RefluxChannelError`/`ParamHealthError`/`DecisionCredentialError`/`DecisionRequiredError`/`PlanStateError`/`SkillDraftError`/`KnobError`/`PrescriptionError`/`GuardViolation`/`TaskStateError`/`AgentRegistryError`/`WorkflowStateError`/`SkillConflict`（grep：contract/ 下 ≥20 处 `(ValueError)`）。
- **少数用 proper 基类**：`McpServerError(Exception)` 子类树 `ToolNotExposed`/`AuthDenied`/`ConfirmRequired`/`ConfirmTokenInvalid`（`mcpserver/__init__.py:41–62`）、`ScenarioRegistryError(Exception)`（`scenario/registry.py:81`）、`DomainInjectionError(Exception)`（`domain/__init__.py:24`）、`DBConfigError(RuntimeError)`（`store/dsn.py:34`）。
- **残留 legacy**：`workflow/__init__.py` 的 `WorkflowErrorCode` 族 + `WorkflowStateError(ValueError)` + `WorkflowError(Exception)`（注释"忠实吸收；保留定义，不进公共门面 `__all__`"）。

### 2.2 缺口（横切不一致）

- **G1（最重）**：契约层 `(ValueError)` 继承使 `except ValueError` 无差别吞掉全部契约错误 ⇒ **机器不可路由**——正是 `errors.py` 文档点名要消灭的反模式，但决策层修了、契约层没修。
- **G2**：无统一基类；约 30 个类平铺 re-export，消费方无法按"层/域"归类路由。
- **G3**：错误语义与契约 invariants 常量未挂钩（如 `QUOTA_INVARIANTS` 与 `QuotaGateError` 分离），缺"invariant 名 → 错误码"映射。

### 2.3 标准化方案（Batch-7 实施，本稿只定方案）

- 引入内核统一基类 `KernelError(Exception)`，携闭集 `code`（沿用 `DecisionError` 的 code 范式，扩为内核级码表：`CONTRACT_VIOLATION` / `ENGINE_FAULT` / `NOT_FOUND` / `PERMISSION_DENIED` / `CONFIRM_REQUIRED` / `CONFIG_ERROR`）。
- 契约层错误改为继承 `KernelError` 并赋 `code`；`ValueError` 仅保留给"纯输入形态错误"（不进机器路由）。
- 门面 re-export 增加 `KernelError` 与 `KERNEL_ERROR_CODES`；契约 invariants 常量与错误码建映射（守卫测试对拍：删映射分支→转红）。

### 2.4 验收判据

- 变异自证：构造"契约错误被 `except ValueError` 误吞未路由"用例→红线（捕获后未路由即 fail）；删 `code` 分支→转红。
- lint 门禁：grep 契约层新增错误类不得再 `(ValueError)`（纯输入校验除外）。

## 三、横切盘点二：配置注入

### 3.1 现状

- **标杆 `store/dsn.py`**：DSN 仅从 env 读、源码零口令硬编码；env 键名模块常量 + 可注入（`dsn_env`/`dsn_test_env`/`schema_env`）；红线 `FORBIDDEN_HOSTS`/`FORBIDDEN_ROLES`；取数即校验；`mask_dsn()` 唯一日志形态（`dsn.py:10–211`）。
- **散读**：`llm/tier.py:131/138/140/145/174`、`vector/embedding_api.py:48/60/64/100/124–128`、`vector/infer.py:131/138/141/148/176`、`vector/onnx_runner.py:55` 直接 `os.environ.get("CHIYU_LLM_TIER"/"CHIYU_EMBEDDING_*"/"CHIYU_MODEL_DIR")` 且各自带 `DEFAULT_MODEL`/`DEFAULT_BASE_URL` 散落默认；`CHIYU_TEST` 在 `dsn.py`/`embedding_api.py`/`infer.py` 多处独立读取。

### 3.2 缺口

- **G1**：无统一配置访问器（除 `dsn.py` 外）；键名命名空间不一致（`CHIYU_DB_*` vs `CHIYU_LLM_*` vs `CHIYU_EMBEDDING_*`）；LLM/向量配置无校验、无 mask、无"键名注入"。
- **G2**：测试标记 `CHIYU_TEST` 多模块独立读，无中心化（与 `dsn.py` 的 `in_testing_context()` 逻辑重复）。
- **G3**：`CHIYU_EMBEDDING_API_KEY` 在 `embedding_api.py:127` 用 `os.environ["..."]`（缺省即 `KeyError`），与 `dsn.py`"缺配置即显式抛 `DBConfigError`" 纪律不一致。

### 3.3 标准化方案（Batch-7）

- 抽 `chiyu_kernel/config/` 统一访问器（镜像 `dsn.py` 纪律）：`get_setting(key, default=None, *, validate=..., mask=...)` + 中心化 testing 标记；LLM/向量键名收口为常量；缺必填键显式抛 `ConfigError`（不 `KeyError`）。
- 迁移 `tier`/`embedding_api`/`infer`/`onnx_runner` 的 inline 读取至访问器；`dsn.py` 保留（已达标）作同族。

### 3.4 验收

- 守卫：配置读取路径全过访问器；grep 禁 `os.environ` 直接散读（`dsn.py` 例外）；缺必填键→`ConfigError` 红。

## 四、横切盘点三：租户隔离

### 4.1 现状

- **内核态**：租户隔离 = **schema-per-tenant + `domain` 列过滤**。`PgVectorStore`（`pg_store.py:43`）构造收 `TenantProfile` + `schema`；`pg_memory_stores.py` 以 `profile.domain` 作 `WHERE domain = %s` 过滤（`pg_memory_stores.py:101/122/199/209`）。`TenantProfile` 由 contract 注入，源码零领域字面量。
- **IAM/Web 态**：`iam/rbac.py`（17 处 `tenant_id`）、`web/backend/account_store.py`（12 处 `tenant_id`）以 `tenant_id` 作授权/数据边界。
- **配置红线**：`dsn.py` `FORBIDDEN_HOSTS`/`FORBIDDEN_ROLES` 防越权连库。

### 4.2 缺口

- **G1（命名双轨）**：内核叫 `domain`（persist/profile），IAM/Web 叫 `tenant_id`；同一"租户"概念两套词，跨层对账易错——H-62 的 `ScopePredicate` 注入须显式桥接 `domain`↔`tenant_id`。
- **G2**：内核 `domain` 列过滤依赖"调用方传对 profile"，无中心化"当前租户上下文"；与 IAM 的 `tenant_id` 上下文未打通（web 层手动把 `tenant_id` 转 `TenantProfile` 传入内核）。
- **G3**：H-62 脱域硬点 `assembler.js:292` `CRM_KNOWLEDGE` SQL 内联 `tenant_id=$1`（CRM 侧）；上收后内核须 `ScopePredicate` 注入、`tenant_id` 走参数化（禁字面量）——是 G1/G2 在 context 层的同款命题。

### 4.3 标准化方案（与 H-62 协同）

- **H-62 作为试点**：context 层 `ScopePredicate` 注入 + `domain`/`tenant_id` 桥接契约，确立"租户上下文走注入、内核零字面量"范式。
- **Batch-7 推广**：内核持久/检索层统一以 `TenantProfile.domain` 为唯一租户标识；IAM 侧 `tenant_id`→`domain` 映射留消费方；中心化租户上下文访问器（替代 web 手动传）。

### 4.4 验收

- 守卫：内核 grep 禁 `tenant_id=` 字面量拼 SQL（G-零IO / G-域无关，与 H-62 三硬闸同款）；`domain` 必走参数化。
