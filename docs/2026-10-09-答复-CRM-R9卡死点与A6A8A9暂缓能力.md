## 1. R9 图写 = 卡死点：诚实承认 + 迁移路径重定义

### 1.1 承认：图写语义全量平移 = 确属卡死

CRM 判定成立，无争议。事实链：

- **CRM 图可写**：`src/decision/ageGraph.js` 用 `MERGE`/`SET` 建 Decision 顶点（7 字段）、粒子顶点、6 类依赖边（DECIDED_ON / REFERENCED_PRECEDENT / DERIVED_FROM_EXCEPTION / ESTABLISHES_FRAME / OVERRIDES / CAUSED / INFLUENCED），承载 12 个依赖模块。
- **foundation 图只读**：`graph/__init__.py` 的 `GraphStore` 是只读协议（controlled / out_edges / in_edges / traverse，深度上限 3 + 环检测）；唯一写入口是 `OntologyGraph.link(predicate∈K层)`（受控谓词），`persist.write_decision_memory_net` 是记忆网落库、**非**通用图写。
- **manifest 已如实登记**：`contract/capability-manifest.json` 的 `graph` 条目写明"读 stable；写能力未提供……无通用建节点/边协议（R9 未排期，CRM 图写场景无接缝）"。

F-02 以新形态复归——不是"有无 AGE 等价查询"，而是"**图写语义没地方接**"。此判定**成立**，且未虚构"已提供写能力"。

### 1.2 但"卡死"的范围必须界定

> 卡死的是**图写语义的底座化**，不是**全量迁移**。

原因：

1. **图读已可迁**：`GraphStore` 只读协议 + `InMemory`/`PgCte` 只读实现已 stable，CRM 的图**查询**语义（多跳遍历 / 关系派生 / 时间线 / 回链视图）可平移，不卡。
2. **图写留在 Node 是零成本**：CRM 已有 `ageGraph` 完整实现，迁移进底座反而要新增可写图库——**破坏"单源"纪律**（`graph/__init__.py` 禁另起可写图库，否则双写）。留 Node 是当前最优解，非回避。
3. **单源纪律是硬约束**：底座若新增 `WritableGraph` 与 `persist.write_decision_memory_net` 并存，即双写风险。故 R9 的"解"必须走 deprecation 周期 + 单源裁定，不能草率平移。

### 1.3 迁移路径重定义（建议 CRM 采纳）

把"全量底座迁移"拆成 **可迁面 + 排除面** 两层，R9 图写单列为排除面：

| 层 | 内容 | 状态 |
|---|---|---|
| **可迁面** | 决策脊柱 `run_spine` / 三态审批 / 红线 / 落库 / 向量 / 情境装配 / 图**读** / MCP 客户端桥 | 底座已 stable，试点可直接接 |
| **排除面（消费方自建）** | 图**写**（ageGraph）/ 记忆 / MCP 真 transport / 细粒度授权 | 留 Node 自建，底座给协议/骨架 |

这一定义下：

- **R9 不阻塞试点启动**（已定方案 C：图写留 Node + 纳入试点排除面，`docs/2026-10-09-R9图写能力状态与排期决策.md` §3/§4）。
- **R9 不阻塞 1.0 实证**：1.0 判据硬门槛是"生产 ≥4 周（或暴露量导向）+ P0/P1 清零 + 真库 E2E + 升级演练"（见 `docs/release/v1.0-发布判据.md`），均不依赖图写底座化。
- **中段路线**：试点期评估方案 A（受控写谓词覆盖 6 类边型）→ 据实决定 A→B（WritableGraph 单源），全程守"单源"纪律 + deprecation 周期 + R2 判据规格新增写判据。

**对 CRM 的请求**：把"全量迁移"改写为"分层迁移计划"（可迁面时间表 + 排除面自建清单），图写作为排除面单列跟踪。R9 不再作为"整体卡死点"，而是"单项已知排除面"。

## 1.4 修正（回应"AGE 是否通用"）：决策图模型是底座通用资产，非 CRM 专属

CRM 质疑 R9 是"CRM 专属、被最大公约数排除"——**此质疑成立，上一轮"领域特有"表述需修正**。证据：

- `contract/memory.py` 的 `MEMORY_PREDICATES`（DECIDED_ON / REFERENCED_PRECEDENT / DERIVED_FROM_EXCEPTION / ESTABLISHES_FRAME / OVERRIDES / CAUSED / INFLUENCED）与 CRM `ageGraph.js` 的 6 类边**逐字一致**（consumability-design.md:23 实锤）。
- 抽取计划 T1–T5′ `:71` 早把这批谓词判为"**进内核（记忆上下文图谱通用）**"——决策图模型本就是底座自己的通用词汇，不是 CRM 发明。
- 底座**已有通用图写原语** `OntologyGraph.link(predicate, _from, _to)` + K 层受控谓词（`ontology/graph.py:79/82`），谓词由 `TenantProfile` 注入，零领域字面量。
- 成熟度蓝图 `:224` 明定 `PgCteGraphStore` = "AGE 等价能力"；`:226` "内核不内置 AGE 适配器"是**可测性纪律**（无 AGE 服务即不可测=假绿），非"模型专属"。

**结论**：AGE 是**引擎**，决策图**模型**是底座通用资产。对 APS/enterprise **有真实价值**（三家皆做决策，决策记忆图是底座词表，均可复用）。故 R9 **不是**"CRM 专属排除面"，而是**底座补充候选（通用形态）**——这正是 R9 中段 A→B 的本质（受控写谓词覆盖边型，而非抄 CRM 域模型）。

短期仍排除的四个**工程/时序**约束（非"领域专属"）：
1. `OntologyGraph` 是**纯内存**（dict，无 PG 持久化）——缺 PG 落库的可写图；
2. 缺**顶点属性写**（CRM `SET n.scenario_id` 7 字段），`link()` 仅建边；
3. 单源：`persist.write_decision_memory_net` 是唯一 PG 图写路径，新增可写图=双写风险；
4. 底座"不内置 AGE"=测试纪律，CRM 可续用 AGE 作引擎或迁底座 PG 图。

## 2. A6 记忆 deferred：与 R9 同类的"实验态排除"

> **结案更新（T44，2026-10-10）**：A6 已按 §2.3 列出的五件毕业工程全部落地（T40 双轨 PG 落库 / T41 召回接入 `run_spine` / T42 RRF 多源融合 / T43 真库 E2E / T44 单源裁定），`memory` 转 **stable**、进入 1.0 兼容承诺，`MEMORY_EXPERIMENTAL = False`。**A6 从本回执的排除面中移除**——CRM 可直接选用底座记忆能力，或继续自建（两者均合法）；下文 §2.1–§2.3 保留作决策留痕。

### 2.1 事实（毕业前留痕）

- `memory` 层在 manifest 中登记为 **`experimental`**（`contract/capability-manifest.json`：`("memory","experimental")`，双轨记忆运行时 2026-10-09 已落地但 **T5′ 未整体验收，不得写硬判据**）。
- foundation 口径：`memory` / `evolution` 均**排除出 1.0 兼容承诺**（`docs/release/v1.0-发布判据.md` §1 A 类），也**不进入 CRM 试点范围**（`docs/2026-10-09-foundation邀请-致CRM(1.0生产实证接入·主证据源).md`：memory/evolution 维持 experimental，试点面最小化）。

### 2.2 对 CRM 的含义

CRM 的"记忆 deferred"与 R9 是**同一模式**：

- 底座不提供生产级记忆 ⇒ CRM **不能依赖 foundation memory 做生产记忆**；
- 路径二选一：① **消费方自建记忆层**（同图写 C 模式，Node 侧已有记忆实现）；② **等 memory 从 experimental 毕业**（毕业时：T44，2026-10-10——**已发生**，见 §2 结案更新）。
- 任何选择都属于"排除面 + 自建"，不阻塞试点与 1.0。

**承诺（T44 起已兑现）**：foundation 对外提"决策记忆网"时，如实声明其判据面（真库 E2E `test_memory_e2e.py` + 单源裁定守卫 `tools/check_single_source_memory.py`），不虚构超出判据面的能力。

### 2.3 memory 从 experimental 毕业还需哪些任务（用户追问：这可是基础能力）

memory 标 experimental **不是因为不重要，而是消费路径没接通**。源码核实发现两层事实：

**事实一：计划与实现已漂移**。T5′ 计划要求建 `memory/{store,fingerprint,precedent,recall,fuse}.py` 包，**实际未建**；落地的是 `persist/memory_tracks.py`（T20 双轨运行时），结构被整合缩减。

**事实二：已 embody 的比计划最小集多**。`memory_tracks.py` 已有：双轨（LOG append-only + NOTE upsert + content_hash 幂等）+ 周期蒸馏（`distill()` 显式优先 + 价值视界 两闸）+ `PRESCRIBABLE_PREDICATES` 白名单（与 `judge_worthiness` 写侧两闸拼合为完整四闸，import 期 fail-fast）。

**仍缺（毕业必需）**：
1. **召回消费点（最大缺口）**：记忆写了、蒸馏了，但**未接进 `run_spine`/context 的决策回路**——决策时并不读记忆。写了不读=没用，这正是它还不能称为"基础能力"的根因（计划 `:2808` 自承"召回消费点缺失"）。
2. **PG 持久化本体**：`memory_tracks.py` 只给内存参考实现 + 契约测试（`CHIYU_TEST_DSN` 缺席即 skip），PG 绑定"由消费方适配"——底座未 ship 真正的 PG 记忆落库。
3. **分层检索 / RRF fuse**：计划的 `recall.py`/`fuse.py` **未建**，蒸馏产物没进决策上下文。
4. **真库 E2E**：回归套件全 FakeStore；memory 需 `@pytest.mark.pg` 的真库往返（持久化 + 召回）测试沉淀。
5. **契约稳定化 + 单源裁定**：与 `OntologyGraph.link` / `write_decision_memory_net` 收口防双写，去 `experimental` 标，进 G1/A7 验收，写硬判据（当前"不得写硬判据"）。

**结论**：memory 毕业是**5 件具体工程**（召回接入 → PG 落库 → 检索/fuse → 真库 E2E → 去 experimental），其中"召回消费点"是让它成为真正基础能力的关键一跃。它不是"再等等"，而是有清晰路径的待办。

## 3. A8 MCP transport：已闭合的 consumer self-build 范式（非阻塞）

### 3.1 事实

- foundation 提供 `McpTransport` **协议** + `McpBridge` 编排 + `InMemoryMcpServer` 替身（`chiyu_kernel/mcp/__init__.py:25/77/37`）。**真 transport（stdio 网络 / Streamable HTTP）无排期**——`mcp/__init__.py:4` 明示不在本阶段。
- 已为 CRM 出具 **R5 接口契约**（`docs/2026-10-09-MCP-transport接口契约-R5.md`）：四方法协议 + 生命周期状态机 + 命名契约 + 错误语义 + 回捐验收。**该契约本身就是 extension point**。

### 3.2 结论

A8 **不是阻塞，是已闭合的"消费方自建 + 回捐范式"**：

- CRM 自实现 Node transport，按 R5 契约四方法 + 状态机 + `normalize_mcp_name` 逐字节一致 + 错误不静默 ⇒ 即可接入 `McpBridge`，无底座改动。
- 回捐形态：Node transport 实现 + 命名函数等价件 + E2E 测试记录；底座侧以契约为准复核，不逐行对拍。

**对 CRM 的请求**：A8 按 R5 契约推进即可，无需等 foundation。若需补强，建议把"回捐验收"做成自动化 parity 测试（同一 transport 接口，替身 server 跑 connect→list_tools→call_tool→disconnect）。

## 4. A9 授权自建：扩展点已就位，域逻辑消费方填

### 4.1 事实

- CRM 授权模型比 foundation 细：`src/mcp/` 对 `src/rbac.js` 引用 = 0，MCP 走 `gateway.js:284` 与 `intent.js` 的 per-Action `rbac_roles`，`executor.js:91-96` 又各判一次（同语义多通道分裂，CRM 内部 A5 项）。
- foundation 提供 **MCP 服务端骨架** `McpServer`（`chiyu_kernel/mcpserver/__init__.py`），内建三道护栏：
  1. **零信任鉴权**：`auth` 未注入 ⇒ 一律 `AuthDenied`（默认拒绝，非默认放行，`:174`）；
  2. **两阶段确认（写操作）**：`ConfirmRequired` + `confirm_token`，令牌**绑定（工具名, 参数, 主体）三者**，改任一即失效（防重放，`:179-187`）；
  3. **传输无关派发**：`handle_request()` 是 JSON-RPC 风格派发器，任何 http 框架直接喂（`:142`）。

### 4.2 关键 extension point = 可插拔 `auth(ctx) -> bool`

`McpServer.__init__(auth=..., secret=...)`（`:111`）声明：**鉴权是可插拔函数，由消费方注入；内核不发明账号体系**（`:11`）。这正是 CRM 细粒度授权的接入点：

- CRM 注入自己的 `auth`，内部调 `rbac.js` 的 `can*` 纯函数（接收 `{actor, role, tenantId, scope}`）；
- 顺带**闭合 CRM 内部 A5（HTTP/MCP 授权同源）**——把角色决策收敛到 `rbac.js` 单一源，MCP 侧不再各自判；
- 写操作的两阶段确认底座**已内建**，CRM 无需重造。

这与已落地的 **`run_spine` 注入范式**（T10：`redline_callback` / `context_factory` 钩子形态=foundation 公共能力，钩子内域逻辑=消费方自建）**完全同构**——"扩展点形态收敛到底座，域判断留给消费方"。

### 4.3 唯一待补：A9 接入契约成文

`auth` 钩子目前**隐含在骨架里，未像 R5 那样独立成文**。建议下一轮补一份 **《MCP 服务端授权接入契约》**（与 R5 同体例）：明确 `auth(ctx)` 入参语义、零信任默认拒绝、两阶段确认与 `risk='write'` 的绑定、CRM `rbac.js` 收敛到的 `can*` 纯函数接口。这能让 CRM 的 A9 从"读骨架源码"降级为"对齐契约"。

## 5. 共性模式：四项的纪律提炼

R9（图写）/ A6（记忆）/ A8（transport）/ A9（授权）**共享"底座给协议/骨架 + 消费方填域逻辑或自建"的对接形态**，但严格说分两类：

- **通用资产、短期工程缺口**：R9（决策图模型是底座 `MEMORY_PREDICATES` 通用词表，缺的是 PG 可写图 + 顶点写 + 单源，是底座补充候选，见 §1.4）——仍是底座该补的候选；~~A6~~ **已毕业（T44，2026-10-10）**，从本类移除。
- **机制/策略分离 + 环境绑定**：A8（transport 环境绑定，协议已给）、A9（auth 机制已给、策略消费方填）——这两项底座**不该**吸进域逻辑，排除面是正确终态。

| 项 | 底座给什么 | 消费方做什么 | 登记状态 |
|---|---|---|---|
| R9 图写 | 只读 `GraphStore` + `OntologyGraph.link` 受控谓词 | 图写留 Node 自建（ageGraph） | 排除面（方案 C 已定） |
| A6 记忆 | 双轨 PG 记忆 + 召回接入 + RRF（T40–T44） | 可直接用底座记忆，或仍自建 | **已毕业转 stable，移出排除面** |
| A8 transport | `McpTransport` 协议 + 契约 | 自实现 Node transport 回捐 | R5 契约已闭合 |
| A9 授权 | `McpServer` 零信任 + 两阶段 + `auth` 钩子 | 注入 `rbac.js` `can*` 纯函数 | 扩展点就位，契约待补 |

**纪律（foundation 边界）**：凡标记为 `experimental` / 未提供 / 协议态的能力，消费方一律走"**自建 + 排除面登记**"，**不得等底座**。底座的职责是给 stable 抽象 + 明确的 extension point（协议/钩子/骨架），域判断（角色、记忆、图写语义）是消费方资产，不该被底座吞掉——这也正是 foundation 定位"公共能力底座、一次做成多次复用"的边界所在。
